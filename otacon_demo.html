how it works

You ask. HAL decides which tools to use.

web · voice · chat→HAL core→brain→tools→Otacon

There's no script deciding what a message "is". The model reads the request, picks the tools it needs, chains them, and answers in Otacon's voice.

Honest by design. When HAL doesn't know something, he checks his memory and then says so instead of inventing an answer.

what I've built

The engineering under the hood

HAL is a working system I use every day, so most of the work is making him reliable, safe with my data, and cheap enough to run.

agent

Real tool use

The model reads each request, chooses the tools it needs and chains them together, instead of following keyword rules.

memory

Layered, searchable memory

Recent conversation, a stable profile, and semantic search across my notes and documents, with embeddings running locally. Newer facts win over old logs.

safety

Nothing saved without a yes

Changes to stored notes are held as drafts, shown word for word, and only written once I approve them.

briefings

Reliable background jobs

Daily inbox and calendar sweeps arrive as a briefing, and are only marked delivered once they've actually reached me.

cost

About 85% cheaper per message

The stable part of HAL's instructions is cached and history is trimmed by size, so each message sends far less to the model.

process

Checkpoints and tests

Every change happens on a branch with a tagged checkpoint to roll back to, and has to pass behavior tests in plain conversation before it ships.

architecture

Brains are replaceable. HAL is not.

  • Doorways are thin.Web, voice and chat call one function and get back a reply, an emotion for the avatar, and any generated document.
  • The brain is a plug.Switching models can't change Otacon's personality, memory, tools or permissions.
  • Paid API never kicks in silently.If the default runs out, HAL asks before switching.
  • Python + FastAPI on an Intel NUC.Local embeddings on the NUC, a separate GPU machine for local models.

how I work

How I work, and what's next

  • Snapshot first.Branch, tag and verify backups before any change that matters.
  • Test behavior, not implementation."Doesn't make up facts about strangers" outlives any code path.
  • Restore, then optimize.Never cut capability just to save money.
  • Anything permanent gets confirmed.Show the exact change before writing it.
  • Finish each phase.Every phase ends with a passing test and a tag.
